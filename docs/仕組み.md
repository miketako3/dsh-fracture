# 仕組み

この文書は、dsh-fracture が内部で何をしているかを説明します。
README が「何ができるか」を、この文書が「なぜそうなっているか」を担当します。
読み終えると、どの変更が自動で入り、どれが人間の判断を待つのかを、理由つきで説明できるようになります。

## 1. 全体像

```mermaid
flowchart TB
  subgraph 走り続ける部分
    E[ターンが終わる] --> O[観察を1行追記]
    O --> D[20ターンごとにダイジェスト]
    O --> K[3回連続で成功した手順を<br/>スキルにする]
    D --> P[プロンプトの索引]
    K --> P
  end
  subgraph 測ってから変える部分
    P --> X[診断]
    X --> Y[提案]
    Y --> Z[試行]
    Z -->|改善| W[適用と監視]
    Z -->|改善せず| N[捨てる]
    W -->|悪化| R[取り消し]
  end
```

エージェントの応答は、DSH が毎回組み立て直します。
そのため、走っているセッションにプロンプト節を一つ足せば、次の応答から振る舞いが変わります。
fracture はこの性質を使って、再起動なしにハーネスを変えます。

ただし、プリセット（行の並び）そのものは空のセッションにしか結び付けられません。
走ったことのあるセッションに別のプリセットを結び直すと、そのセッションは壊れます。
自動適用がプロンプト節に限られているのは、この制約のためです。

## 2. 4つの段

変えてよい深さを、危険度の順に四つに分けています。

| 段 | 変わるもの | 試行 | 承認 | 戻し方 |
| --- | --- | --- | --- | --- |
| T0 記憶 | 観察、ダイジェスト、ジャーナル | なし | なし | ファイルを消す |
| T1 スキル | `skills/<slug>/SKILL.md` と実行中の登録 | なし | なし | ファイルを消す |
| T2 構成 | プロンプト節、スキルの置き場、ツールの切り替え | 必須 | なし。監視して悪化すれば自動で戻す | 節を外す |
| T3 コード | プラグイン本体、フック、UI | 必須 | **人間** | バンドルを外す |

T0 と T1 は知識です。
実行もできず、権限も広げられず、ファイルを消せば元に戻るので、断らずに走ります。

T2 は振る舞いを変えるので、証拠として試行を要求し、そのあと監視期間を置きます。
それでも断らずに走るのは、プラグイン自身が持ち、自分で取り消せるデータの変更だからです。

T3 はプロセスで動くコードを決めます。
ループは書くところまでと試すところまでを自動でやりますが、入れるかどうかは人間が決めます。
自動で入れられると、ループはシステムで最も強い権限を持つ主体になり、最初の悪い変更を内側から反証できなくなります。

## 3. ループの4つの道具

自動で回る場合も、手で呼ぶ場合も、同じ4つを使います。

```text
fracture_diagnose → fracture_propose → fracture_probe → fracture_adopt
     証拠              候補             対比            成果物
```

### 3.1 診断

診断は、保存されたセッションイベントに対する算術です。
意見ではなく、数を出します。

| 見るもの | 数え方 |
| --- | --- |
| ツールの失敗 | 呼び出し回数と失敗回数。失敗率の順に並べる |
| 同じファイルの読み直し | 1セッション内で同じパスを3回以上読んだ回数 |
| 承認の拒否 | 拒否された承認の件数 |
| 文脈の圧縮 | 圧縮が起きた回数 |
| メッセージの評価 | フィードバックが記録されている場合の評価 |
| トークン | プロバイダが使用量を返す場合の合計 |

一度の不運な失敗が所見にならないよう、下限を置いています。
ツールは3回以上の呼び出しと30パーセント以上の失敗率、同じパスは3回の読み直し、拒否は2件です。

評価は既定で信頼します。
評価は回答に対する人間の発言であり、低い評価は手に入る中で最も強い安価な信号です。
ただし、それだけでは足りません。
所見は数で説明できなければならず、評価だけでは何を変えるかが決まらないからです。

### 3.2 提案

提案は、その変更と暮らすことになるセッションではなく、**サブエージェント**が行います。
理由は二つあります。

一つは文脈の隔離です。
提案役はリポジトリと診断結果を読めますが、その探索の記録が作業中のセッションを汚しません。

もう一つは責任の分離です。
提案役はファイルを書き、親が検証します。
提案役が失敗したときに残るのは、はじかれた候補であって、壊れたハーネスではありません。

提案役は何も導入できません。
出すものはディレクトリ一つです。

```text
candidates/<id>/
├── candidate.json      # 行、根拠、所見、レバー、任意の検証コマンド
├── skills/<name>/…     # 任意
└── plugin/index.js     # 任意
```

検証はサブエージェントが戻ったあと、親が行います。
JSON の形、行の数、触ってはいけない範囲かどうかを見ます。
はじくときは、間違いを一度に全部伝えます。
そうしないと、やり直しの材料が残りません。

### 3.3 試行

ここがループの値打ちであり、制約が最も多い場所です。

試行は、同じ仕事を今のハーネスと候補の両方で走らせ、比べます。
プロンプトの文面、ワークスペースの中身、使えるツールは同じで、違うのは候補の行だけです。

実行の経路は二つあり、どちらになるかは候補が `plugin/` を持つかで決まります。

| 候補 | 走る場所 | 理由 |
| --- | --- | --- |
| 行だけ（プロンプト節、スキルの置き場、切り替え、既存ツール） | DSH プロセス内の子エージェント | 参照するモジュールはすでに読み込まれている。新しいコードは実行されない |
| コードを含む（`plugin/index.js`） | 別の `dsh` プロセス | 検証していないコードを、それを判定するセッションと同じプロセスで動かさない |

```mermaid
sequenceDiagram
  participant P as 親セッション
  participant B as 基準のハーネス
  participant C as 候補のハーネス
  participant V as 検証コマンド
  P->>B: 同じ仕事を渡す
  B-->>P: 軌跡
  P->>C: 同じ仕事を渡す
  C-->>P: 軌跡
  P->>V: 両方のワークスペースで実行
  V-->>P: 終了コード
  P->>P: 判定を書く
```

ワークスペースは左右で分けます。
試行の仕事はたいていファイルを書き換えるからです。
`node_modules` と `.git` を複製すると費用が支配的になるので、複製ではなく元へシンボリックリンクを張ります。
ビルド成果物（`dist`、`build`、`.next`、`target` など）は複製せず、fracture 自身の作業ディレクトリも除外します。
試行が過去の実行結果を自分の中に写さないようにするためです。

判定は、候補が検証コマンドを宣言している場合、その終了コードで決まります。
宣言がない場合は `needs-review` になり、両方の軌跡を人間に見せます。
別のモデルに採点させる案は将来の追加候補ですが、測る前にループの最も重い判断を任せるわけにはいきません。

両側の軌跡は `[ACTION]` と `[OBSERVATION]` の組で書き出します。
これは Harness² の考え方で、コードは借りていません。
二つの実行を目でも差分でも比べられるようにするためです。

### 3.4 導入

試行の結果は証拠であって、許可ではありません。
だから導入は別の道具にしています。

- 直近の試行が `improved` でなければ断ります。`force` を付けた場合だけ通します。
- バンドルを作ります。`cordis.patch.yml`、`dsh.bundle.patch` を宣言した `package.json`、候補の `plugin/` と `skills/` です。
- 候補からの相対パスで書かれた行は、バンドルのパッケージ名に書き換えます。ファイルは同じで、読み込み方だけが変わります。
- `lessons.md` に一節を追記します。
- 導入そのものはしません。導入は `dsh plugin add` か `plugin_manager` ツールで、この承認が自己改変に対する人間の関門です。

自分の設定ファイルに行を並べたい人のために、プロファイルのパッチに追記する道も用意していますが、既定では切りません。

## 4. いつ動くのか

| きっかけ | 動く段 | 頻度 |
| --- | --- | --- |
| ターンの終わり | T0 | 毎ターン |
| ターンが8回進んだ | T1、T2 | 窓ごとに一度まで |
| セッションの終わり | T0 の要約、T1 | セッションごとに一度 |
| 15分のアイドル | T1、T2 | ターンが動いていないときだけ |
| ツールを手で呼ぶ | すべて | 要求があれば |

利用者とぶつからないように、次の決まりを置いています。

- ターンが動いている間に試行を始めない。
- 同時に走るループは一つだけ。
- T2 の変更を適用したら、監視期間が終わるまで次の T2 を始めない。
- 内部の失敗が2回続いたら、autonomy を `memory` に落とし、理由をジャーナルに書く。

## 5. 適用と監視

```mermaid
flowchart LR
  A[適用] --> B[直近12ターンを基準に記録]
  B --> C[12ターン待つ]
  C --> D{比べる}
  D -->|悪化| E[節を外す]
  D -->|変化なし| F[そのまま残す]
  E --> G[ジャーナルと通知]
```

適用した時点で、直前 `watchTurns` ターンの指標を基準として記録します。
監視期間が来たら、適用の刻印より後に記録されたターンだけを比べます。

| 指標 | 取り消す条件 |
| --- | --- |
| ツールの失敗率 | 5ポイントを超えて上がった |
| ターンあたりの手順数 | 25パーセントを超えて増えた |
| プロンプトのトークン | 15パーセントを超えて増えた |

取り消しもまた変更です。
記録し、通知し、数えます。
2回続けて取り消したら、そのセッションでは T2 を止めます。

監視の目的は、変更が良かったことを証明することではありません。
悪い変更の代償を、一週間ではなく監視期間一回分にすることです。

## 6. 触らせない範囲

ループは、自分を縛る規則を変えられてはいけません。
`src/guard.ts` は、次の名前を含む行を持つ候補をはじきます。

| 対象 | 理由 |
| --- | --- |
| `dsh-user-approval` | 承認を弱める候補は、以後のすべての候補を通しやすくする |
| `dsh-sandbox-policy` | 同様。ファイルとプロセスの境界を動かす |
| `plugin_manager` | パッケージを入れられる候補は、何でも入れられる |
| `dsh-fracture` | 走っている間に自分を書き換えると、対象が定まらない |

判定は名前の部分一致なので、保守的です。
`approval` を含むだけの無害な行もはじきます。
誤ってはじく代償は提案一回分ですが、誤って通す代償は境界そのものなので、この偏りは意図しています。

## 7. 後始末

試行が持ち、試行より長生きしてはいけない資源が二つあります。

| 資源 | 解放しないとどうなるか | いつ解放するか |
| --- | --- | --- |
| 候補のプリセット | 登録が残り、次の試行の番号がずれる | `finally` で、登録時の disposer を呼ぶ |
| 子エージェント | 走りっぱなしになり、トークンを消費し続ける | `finally` で、結果を待ってから `dispose()` する |

プリセットの登録は失敗しても例外になりません。
登録簿に `broken` として記録され、登録自体は成功したように見えます。
この確認を省くと、試行は基準の行を走らせて、読み込まれなかった変更の結果を報告します。
だから試行は、登録したプリセットを読み直し、壊れていれば中止します。

## 8. 計測していること、していないこと

| 計測する | 出どころ |
| --- | --- |
| ツールの呼び出しと結果 | セッションイベント。失敗の種類も含む |
| 承認の判断 | 承認イベント |
| 圧縮の回数 | 圧縮イベント |
| トークン使用量 | アシスタントのメッセージ |
| メッセージの評価 | フィードバックのプラグインが入っている場合 |

次の二つは、まだ計測していません。

- **導入前後の初回プロンプトのトークン数。** `ctx.tokenMeter` で取れますが、配線していません。それまでは、導入したプロンプト節の費用は未検証です。
- **採点による判定。** 3.3 のとおり、決定的な検証コマンドを優先します。

## 9. 採用しなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| DSH を fork してループを組み込む | 成果物が動く標的に追随できず、利用者は入れられない |
| Harness² を同梱して形式を変換する | ハーネスの語彙が二つになる。実行環境は Python で、配るのは Node でなければならない |
| 試行が良ければ提案役に適用させる | 人間の関門が「コードを入れる」から「モデルの要約を信じる」に移る |
| 両側の試行を同時に走らせる | 同じ割当を奪い合って待ち時間の比較が意味を失い、後始末も複雑になる |
| `subagent` ツールでプリセットを渡す | `allowedAgentPresets` は読み込み時に確定するので、実行中に登録したプリセットは受け付けられない |

## 10. 実装状況

| 部分 | 状態 |
| --- | --- |
| 観察の記録 | 済。`src/observe.ts` と `src/autopilot.ts`。`turn/end` で動く |
| 記憶のダイジェスト | 済。数と順位だけで書く。`digestEvery` ターンごとに書き直す |
| 索引の節と検索 | 済。動的な `systemPrompt.section`（順序 9900）と `memory_search` |
| スキルの蒸留 | 済。2段以上の手順が3回連続で成功したとき。手書きは上書きしない |
| 走っているセッションへの登録 | 済。`agent.ctx.skills.register`。蒸留のたびに差分を合わせる |
| 試行を経た T2 の適用 | 済。プロンプトだけの候補に限る。行を持つ候補は理由を返して断る |
| 監視と自動の取り消し | 済。`openWatch` が基準を記録し、`evaluateWatch` が比べる |
| セッション内の通知 | 済。`src/notice.ts`。折りたたまれた行として出し、ターンは起こさない |
| 予算の計算 | 済。`src/policy.ts` が数え、`src/autoloop.ts` が参照する |
| 自走ループ | 済。15分のアイドルか `fracture_loop` から回る |
| T3 の作成と引き渡し | 手で回す場合のみ。引き渡しはツールの返り値 |

## 11. ホスト側の前提

API の表面からは分からないが、実装が依存している事実です。

| 前提 | 影響 |
| --- | --- |
| 節は `preStep` の `assemble()` ごとに描画し直される | `text` を関数にすれば、内容がその場で変わる |
| `complete: true` を付けた節があると、他の節が黙って消える | このプラグインは決して付けない |
| `ctx.skills.register` は同名で最初のものが勝ち、登録簿の版を上げる | 差分だけを合わせる。ステップごとに登録しない |
| `agent.ctx` への登録はそのエージェント限り、プラグインの文脈への登録は全体 | 記録は前者、共有は後者 |
| 走っているエージェントの構成は結び直せないが、次の要求は毎回組み立て直される | 自動適用はプロンプト節に限る |
| `agent.inject` はターンを起こさない。`agent.followup` は起こす | 通知は `inject`。ループが自分でターンを作ることはない |
| `source.kind` が `user` でないメッセージは文脈として描画される | 通知が人間の発言に見えることはない |
